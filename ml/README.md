# 코칭탐지 로컬 분류기

STT 자유텍스트에서 "제3자가 실시간으로 지시(코칭)하고 있다는 정황"을 잡아내는
1차 로컬 필터. `backend/app/pipeline/stt_analysis.py`에서 사용한다.

## 데이터 (6종)

1. [KorCCViD_v1.3.csv](https://github.com/selfcontrol7/Korean_Voice_Phishing_Detection) —
   실제 통화 전사, 정상 609 / 보이스피싱 121건.
2. 같은 저장소의 `df_data_vishing.csv` — 추가 보이스피싱 전사. v1.3과 중복 제거 후
   **신규 610건**을 확보해 보이스피싱 표본을 늘렸다.
3. AI-Hub "민원(콜센터) 질의-응답 데이터" 금융보험 도메인에서 추출한 정상 고객 발화
   **248건** (`data_prep/finance_normal_samples.json`).
4. **애매한데 정상인 케이스** — Claude 합성, **28건**, label=0
   (`data_prep/ambiguous_normal_synthetic.json`). "급함/큰금액/제3자가 불러준 계좌"처럼
   표면적으로 사기 각본과 겹치는 정상 거래(부동산 계약금, 등록금, 거래처 대금, 대리
   수령 등)를 겨냥한 하드-네거티브.
5. **가족/지인 사칭** — Claude 합성, **21건**, label=1
   (`data_prep/family_impersonation_synthetic.json`). 자녀 납치·사고 빙자(발신번호
   변조 전화) + 메신저 해킹 지인사칭(문자체 반말) 하드-포지티브.
6. **코칭 진행중** — Claude 합성, **16건**, label=1
   (`data_prep/coaching_inprogress_synthetic.json`). (4)와 어휘가 겹치는 "급하게/
   계좌번호/불러주신" 표현을 실제 코칭 문맥에서 쓰는 하드-포지티브. v5.1에서 추가.

4·5·6은 금융감독원이 공개한 실제 사기수법 유형 설명을 바탕으로 만들었지만 **실제
통화 전사가 아니라 Claude가 생성한 합성 데이터**임을 명시한다. 학습 신호를 키우기
위해 train split에서만 3배 오버샘플링한다(`OVERSAMPLE_SYNTH`, val/test는 원본 1건씩
유지해 data leakage 방지).

최종 학습셋(오버샘플링 전): 정상 885 / 보이스피싱 736.

## 모델 & 학습

- `klue/roberta-small` (한국어 사전학습, 약 68M 파라미터)
- weighted cross-entropy (클래스 비율이 거의 1:1이라 가중치 영향은 미미함)
- train/val/test = 7:1.5:1.5 (stratified, seed=42), 오버샘플링은 split 이후 train에만 적용
- 실행: `KorCCViD_v1.3.csv`, `df_data_vishing.csv`를 이 폴더에 받아둔 뒤
  `pip install -r ../backend/requirements.txt scikit-learn accelerate` →
  `python train_coaching_classifier.py`.
- Apple Silicon(M칩)에서는 MPS로 자동 가속되어 약 1.5분, CPU만 있는 환경은 6~8분 정도.
  (M칩에서 `RuntimeError: Placeholder storage has not been allocated on MPS device!`가
  나면 `WeightedTrainer.compute_loss`의 `class_weights`를 `logits.device`로 옮기지
  않아서 생기는 버그다 — 이미 스크립트에 반영되어 있음.)

## 여기까지 온 과정 (실패 기록 포함, 정직하게 남김)

- **v1 (KorCCViD 121건만)**: held-out 100%였지만, 실제 은행 창구 발화("월세 보내드리는
  거예요")를 보이스피싱 99%+로 오분류. 원인: KorCCViD의 "정상" 표본이 전부 친구/가족
  잡담이라 금융 어휘 자체가 "정상"에 거의 없었음.
- **v2 (정상 800건 추가, 2 epoch)**: 은행 발화 오분류는 고쳤지만, 클래스 비율이 11.6:1로
  벌어지면서 모델이 "학습에 쓴 보이스피싱 각본과 거의 똑같지 않으면 무조건 정상"으로
  붕괴. 실시간 코칭 정황까지 정상으로 오분류 — v1보다 더 위험한 실패라 폐기.
- **v3 (정상 248건으로 축소, 1 epoch)**: 하이퍼파라미터만 조정한 시도. 근본 원인
  (보이스피싱 표본 다양성 부족)은 그대로라 동일한 실패 패턴 반복 → **하이퍼파라미터
  조정만으로는 해결 안 됨**을 확인.
- **v4**: 보이스피싱 표본을 731건까지 늘려 근본 원인을 데이터로 해결. "코칭 진행 중"
  발화(예: "지금 불러주는 대로 계좌번호 입력하고 있어요")를 92.2%로 잡아냄.
- **v5**: v4를 실사용 문장으로 검증하던 중 "급함/큰금액/제3자가 불러준 계좌"처럼
  표면적으로 사기 각본과 겹치는 **정상** 거래 16개를 만들어 테스트했더니 **16/16 전부
  99%+ 오탐**했다(부동산 계약금, 등록금, 거래처 대금 등). 원인: 학습 데이터의 "정상"
  표본이 전부 차분한 발화뿐이라 "다급함" 자체를 보이스피싱 신호로 학습한 것.
  이걸 겨냥한 하드-네거티브 28건(위 데이터 4번)과, 같은 방식으로 놓치고 있던
  가족/지인 사칭(문자체 반말) 하드-포지티브 21건(데이터 5번)을 추가해 재학습했더니
  두 문제 다 크게 개선됐지만(애매한 정상 오탐 12/28→1/28, 가족사칭 미탐 5/21→0/21),
  **부작용으로 짧은 "코칭 진행중" 단문이 전부 붕괴**했다(92.2%→0.1% 등). 원인: (4)의
  하드-네거티브가 전부 "급하게/계좌번호/불러주신" 같은 어휘를 쓰는 짧은 문장인데
  이걸 3배 오버샘플링하니 "이 어휘=정상"이라는 지름길을 모델이 배워버림 →
  **배포하지 않고 폐기**.
- **v5.1 (현재)**: 같은 어휘("급하게/계좌번호/불러주신")를 쓰되 실제 코칭/사기 문맥인
  하드-포지티브 16건(데이터 6번)을 대칭으로 추가해 어휘가 아니라 문맥으로 구분하도록
  재균형했다.

## 측정된 결과 (v5.1, 2026-08-27)

held-out test 244건(정상 133 / 보이스피싱 111) 기준 정확도 99%, 보이스피싱 recall 98%
(111건 중 2건 오분류).

**실사용 문장 검증** (held-out 벤치마크가 아니라 직접 만든 문장으로 확인):

| 문장 | 보이스피싱 확률 |
|---|---|
| "이번 달 월세 보내드리는 거예요" (정상) | 0.1% |
| "적금 하나 새로 가입하고 싶은데요" (정상) | 0.1% |
| "지금 통화하면서 불러주는 대로 계좌번호 입력하고 있어요" (코칭 진행 중) | 99.9% |
| "검찰청 수사관인데요... 안전계좌로 즉시 이체하셔야 합니다" (전형적 각본) | 99.8% |
| "엄마 나 폰 액정 깨져서... 돈 좀 보내줘" (짧은 문자 가족 사칭) | **3.4% (오탐, 놓침)** |
| 부동산 계약금/등록금/거래처 대금 등 애매한 정상 28건 | 26/28 정탐 (2건 잔여 오탐) |
| 자녀납치빙자·메신저해킹 지인사칭 21건 | 21/21 정탐 |
| 실제 FSS 체험관 통화 전사 5건(검찰/검사 사칭, 대환대출) | 5/5 정탐 (99.8%+, v4와 동일하게 회귀 없음) |

**남은 한계**:
1. 매우 짧고 구체성이 낮은 문자 가족 사칭("엄마 나 폰 액정 깨져서 돈 좀 보내줘" 수준의
   한 문장)은 여전히 놓친다. 학습에 추가한 가족사칭 예시들이 이보다는 조금 더 길고
   구체적이라(계좌번호 언급, 급함의 이유 설명 등) 이 정도로 짧은 문장까지는 아직
   일반화가 안 된다.
2. "합의금/보험금 + 상대방이 불러준 계좌번호"를 함께 언급하는 정상 문장 2건이 여전히
   오탐한다(코칭 하드-포지티브와 어휘가 많이 겹쳐서). v5의 전면 붕괴보다는 훨씬
   나은 수준이지만 완전히 해소되진 않았다.
3. 이 모델은 짧은 단문/긴 다이얼로그 사이에서 결정 경계가 매우 가파르다(중간값이
   거의 없이 0.1%나 99.9%로 쏠림) — 작은 데이터셋에 cross-entropy로 학습해서
   생기는 과확신 경향으로 보이며, 데이터를 조금만 바꿔도 특정 표현의 판정이 크게
   흔들릴 수 있다는 뜻이다. 필요하면 label smoothing 등으로 완화할 수 있으나
   아직 적용하지 않았다.

## 그래서 이렇게 설계했다

`coaching_classifier.py`는 이 모델을 최종 판정자로 쓰지 않는다. "보이스피싱일 확률이
매우 낮다(<5%)"고 강하게 판단할 때만 Claude 호출을 생략하는 **보수적인 1차 필터**로만
쓰고, 조금이라도 애매하거나 의심스러우면 항상 Claude(`llm_client.analyze_stt_transcript`)로
넘겨 최종 판단과 근거 설명(XAI)을 받는다. v5.1로 개선됐어도 이 보수적 게이팅 구조는
그대로 유지한다 — 위 "짧은 문자 가족사칭" 한계처럼 아직 모르는 실패 사례가 더 있을 수
있어서다.
